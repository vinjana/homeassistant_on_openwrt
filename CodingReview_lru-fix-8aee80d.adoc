= Coding Review lru-fix

== Summary

Verdict:: Requires changes
Required findings:: 12
Advisory findings:: 17

The change set migrates the installer from OpenWrt 23.05 (opkg, system Python) to OpenWrt
25.12 (apk, Python 3.13, HA 2026.2). HA now lives in a venv. New options are
`--venv-dir`, `--config-dir`, `--tmp-dir`, `--log-file`, `--db-url` and
`--with-configurator`. It also adds procd auto-restart, a QEMU VM test suite, the bounded
LRU fix and the PyPI download for hass-nabucasa.

A fresh install with the default options works on x86_64 and aarch64 (20/20 and 19/19).
But three things block the change:

* The upgrade path does not work. A second run aborts because `uv venv` refuses an existing
  venv. This was verified in a VM, and it means installs that already leak memory cannot
  get the fix.
* Two new options feed paths into `rm -rf` as root without protection.
* The README's install URL and several of its sections are wrong for 25.12.

Purpose of this review: the developer's own quality check, not an upstream merge request.
Persona findings that the baseline sections already cover are cross-referenced, not
repeated.

== General Defect / Logic Review

[cols="1,3,3,2,1", options="header"]
|===
| # | Context | Problem | Solution | Force

| D1
| `ha_install.sh:318-319`: `pip3 install uv` (unpinned), then `uv venv --system-site-packages --seed "$VENV"`. New.
| **Verified in a VM:** a second run over an existing install aborts with `error: Failed to
  create virtual environment / cause: A virtual environment already exists at:
  /opt/homeassistant` (uv 0.13.7, exit 2). The README's "Upgrading" section and the
  changelog entry tell leaking installs to re-run, so the documented fix for the memory leak
  cannot be applied. Because uv is unpinned, the behaviour also changes with the uv version.
| Pin `uv`, and decide whether to replace (`--clear`) or reuse (`--allow-existing`) the venv. Add a re-run step to the VM test (see T1).
| Required

| D2
| `ha_install.sh:105-111`, `:193-195`, `:885`: `rm -rf "$STORAGE_TMP"` on the value of the new `--tmp-dir`/`HA_TMP_DIR`. New.
| The script deletes the path the user gave, at the start and at the end, as root. A natural
  `--tmp-dir /mnt/external` (the mount point, as with "put it on the external disk")
  deletes the venv, the config and everything else on that disk. `--tmp-dir /root`
  deletes root's home. Raised independently by SO, RMO and Operator.
| Treat the option as a parent: `mktemp -d "$base/ha-install.XXXXXX"`, and remove only that child (ideally from a `trap`, see RM3).
| Required

| D3
| `ha_install.sh:877` `+rm -rf $VENV_SITE_PACKAGES/homeassistant*+`, `:476-477`
  (pycountry), `:454` (`sed` on a glob). These paths were fixed in 23.05; they come from the
  new `--venv-dir`.
| The paths are unquoted. With a space in `--venv-dir`, e.g. `"/mnt/my disk/ha"`, the shell
  splits them, and line 877 runs `+rm -rf /mnt/my disk/ha/lib/...+`, which deletes `/mnt/my`.
  shellcheck flags all three (SC2086).
| Quote the variable part: `+rm -rf "$VENV_SITE_PACKAGES"/homeassistant*+`. Also validate the path options once (see S2).
| Required

| D4
| `ha_install.sh:193-194`: `check_free_space` runs before `rm -rf "$STORAGE_TMP"`. New.
| Leftovers from an earlier failed run count against the 512 MB free-space check, so a retry
  after a failed install is refused needlessly.
| Swap the two lines.
| Advisory

| D5
| `ha_install.sh:85-86`, `:165`, help text of `--config-dir`. New.
| It says that moving the config dir keeps "the SQLite DB" off flash. The DB location is set
  by `--db-url` (default `/tmp`). The README table (`:125-126`) has it right.
| Align the help text and the comment with the README.
| Advisory

| D6
| `ha_install.sh:991-1011`: a re-run without `--with-configurator`. New.
| `/etc/init.d/hass-configurator` from an earlier run stays enabled. An unauthenticated
  editor then keeps starting at boot, although the user turned it off.
| Disable and remove the init script in the else branch.
| Advisory

== Security

[cols="1,3,3,2,1", options="header"]
|===
| # | Context | Problem | Solution | Force

| S1
| `tests/vm-start.sh:53`: `hostfwd=tcp::${SSH_PORT}-:22`. New.
| The forward listens on **all** host interfaces, not just localhost. Together with stock
  OpenWrt's empty root password (SSH works with `BatchMode=yes`, `tests/vm-lib.sh:82`),
  anyone on the developer's network gets a root shell on the VM on port 2222/2223. Through
  QEMU's gateway (10.0.2.2) they can then reach the host's localhost-only services.
| `hostfwd=tcp:127.0.0.1:${SSH_PORT}-:22`.
| Required

| S2
| `ha_install.sh:977-979`, `:1000-1002`, `:916`: `$VENV`, `$HA_CONFIG` and `$HA_LOG_FILE` go unquoted into root init scripts; `$HA_DB_URL` goes into single-quoted YAML. New.
| A space, `;`, `+$(...)+` or `'` breaks the init script or the config, or runs as a command at
  every boot. The operator supplies these values, so no trust boundary is crossed; they are
  a robustness issue more than an attack. A `--db-url` with a password ends up in a
  world-readable (0644) `configuration.yaml`.
| See Q2. For credentials: `secrets.yaml` with mode 0600 and `!secret`, or document "SQLite only".
| Advisory

| S3
| Downloads protected only by TLS: `:481`, `:500-503`, `:532`, `:210-217`. Already known from the earlier review.
| The PyPI simple index already sends `+#sha256=…+` with each link, and `:502` drops it
  with `cut`. `uv`, `wheel`, `netifaces2` and `typing-extensions` are installed without
  version pins (`:318`, `:324`, `:432`, `:528`).
| One `fetch_verified url sha256` helper, and pins (separate task).
| Advisory

| S4
| External storage: README `:134-145`. New.
| On FAT/exFAT sticks the venv and config have no Unix permissions. Physical access to the
  stick then means root code execution at boot, and access to the HA tokens in `.storage/`.
| README: use ext4; physical access means root.
| Advisory

| S5
| hass-configurator when enabled: `:422-427`, `:941-949`. Improved over 23.05 (off by default, warned in the docs).
| It still has no login, runs as root, listens on all interfaces, and `panel_iframe` uses
  plain http. Anyone on the LAN can edit `+/etc/init.d/*+`, which means root code execution.
  (That upstream's `ENFORCE_BASEPATH` defaults to off is unverified.)
| Generate settings with `ENFORCE_BASEPATH`, `ALLOWED_NETWORKS` and `CREDENTIALS`, or state "root for the whole LAN" in the README.
| Advisory
|===
